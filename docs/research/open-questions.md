# Open questions

Every `[unverified]` or contradictory item from the eight research files, grouped by the
file it came from and ranked within each group by how much it blocks implementation:

**cpu > assembler > io > ui > showcase > none**

Each carries the fallback the implementer should use until the item is closed. Nothing
here is a reason to stop — every item has a defined behavior to ship in the meantime.

## How to close an item

1. Open the manual page it cites on bitsavers (`http://bitsavers.org/pdf/ibm/1410/` — the
   consolidated form-number list is in [README.md](README.md)). Read the actual page; do
   not settle for OCR text when the fact lives in a figure.
2. Confirm, refute, or confirm-with-correction. If the manual is genuinely silent, say so
   and record which editions were checked — a verified negative is a closed item.
3. Edit the research file in place: state the corrected fact where the old one was, not in
   a footnote.
4. Update the confidence tag (`[unverified]` → `[likely]` → `[verified]`) and the source
   citation to the form number + page you actually read.
5. Strike the row here, or move it to the resolved note with the answer.

Do not close an item from SimH or cube1us source alone. Emulator code is a second oracle
for *behavior*, not a primary source for *spec* — and both are known to deviate from the
manuals in documented places (see `emulators.md`).

### Wave 2 — emit and pack

`src/asm/emit.ts` owns `encodeAddress` because `src/core/address.ts` exports `addressDigit`,
`decodeAddress`, `resolveIndex` and `checkAddress` and **no encoder**, and keeps `TAG_A_TENS` …
`TAG_B_HUND` module-private. So the index-tag weights now exist twice in this repo. That is **not**
carried as an `OPEN:` constant, because the fact itself is `[verified]` (`architecture.md` §5's
index-tag table and its weights line, A22-0526-3 p.14 Fig. 10) — what is at risk is a
transcription, and the mitigation is a test rather than a ledger row: `encodeAddress` is verified
**only** by round-tripping through the shipped `decodeAddress`, every tag 0-15 over a
boundary-plus-sample sweep, plus the two tagged addresses already sitting in `src/formats/loader.ts`
(`00A?0` = 00100 tag 15 at 00318, `00?!0` = 00000 tag 14 at 00330). If the weights ever move, one
test fails and not two tables.

**Two readings of §8.3's packing sketch, settled in `pack.ts`'s header rather than left implicit.**
The sketch says "for each (addr, cell) in **ADDRESS order**"; the packer walks the items in
**emission order** and each item's cells in ascending address within it. §11.1's backwards-ORG
program is what settles it: its whole point is that the LAST card loads at the LOWEST address so
that its terminating GM-WM lands inside an earlier record, and a globally address-sorted deck would
reorder the cards and make both the warning and the one-byte clobber impossible. A mutation that
sorts globally fails three assertions in `test/tier3-asm-load-equals-memory.test.ts`.

**`pack(items, reserved)` takes two arguments and fills `sequence` only.** §3.1 and §8.3 both pin
the arity, so the `ident` of columns 76-80 — and RESEQ's mid-deck reset of both fields — is applied

**One collision found while building, recorded here because it is mechanical rather than open.**
The alphameric-literal bracket and the x1 overlap-channel character are **the same glyph**: `@` is
BCD `0o14` (`bcd.ts` rank 21) and is both the literal delimiter (`software.md` §3, `[verified]`) and
`X1_CHANNEL`'s channel-1-with-overlap row (`software.md` §10.9, `[verified]`). The REASON the rule
was written is now **historical**, exactly as `operand.ts`'s `literalSpan` JSDoc records it: at the
time, a source deck wrote the x-control field itself, so `RW1 @10,WORK,$` was a legal instruction
whose operand field held exactly **one** `@`. Since 2026-08-31 the assembler SYNTHESISES that field
(`IO_OPERAND_IS_XCONTROL_BADDR_D`, retired), `RW1` is not a mnemonic, and no source deck writes an
x1 glyph at all — so a lone `@` now always ends in an `F`. **The RULE stays and is still
load-bearing**: step 1 reports that a lone `@` **locates no span** instead of flagging it, and the
unmatched-`@` `F` is raised at step 3 rule 3, where the head test can tell an unmatched literal
bracket from anything else and say so far better than step 1 could. Both glyph facts are
`[verified]`; only their interaction needed a ruling, and it needs no constant because either
reading of the interaction contradicts one of them.

**Four judgment calls, recorded so a later wave does not rediscover them.** (1) `Statement.label`
is trimmed at **both** ends: the only legal leading blank is the column-7 indent and
`labelIndented` already carries that fact, while a label with a blank in it is not a label at all
(`software.md` §1: "≤10 alphameric, first alphabetic, no specials"). (2) A **DA header** operand —
`1X80,G` — is a declarative grammar (`software.md` §5, C28-0309-1 pp.13-15) that pass 1 parses off

for §6.3's own reason: you cannot judge an operand before you know the op, which is exactly what
the precedence `O > F` says — and it covers the **more-than-three-operands** flag too, because how
many operands an operation takes is a fact about the operation: `GET A,B,C,D` earns O and no `F`,
while the truncation to three still happens so classification never sees a fourth. (3) `&LABEL&10`
is rule 5's address-constant literal **with an adjustment on the literal's address**, not an `F` —
`software.md` §3 is explicit that "address adjustment and indexing on an address-constant literal
modify the address of the literal, not the literal's value". What rules 5 and 9 key on is which end
the `&` is written at, which is what plan §5.2 says they key on. (4) **An address-constant
literal's `cells` are a five-blank PLACEHOLDER, not its value, and wave 4 must rebuild them.**

known at parse — it is a symbol — so `operand.ts`'s `addressConstantLiteral` returns five blanks
with a word mark over the high-order position, and `Operand.symbol` carries the name. `literals.ts`
has to write the assigned address into those five positions when it flushes the pool; a wave that
reads `Literal.cells` straight through would emit five blanks into core and lose the address
silently. **This is the one of the four wave 4 is most likely to trip over.** With it: `&LABEL`
literals are recorded `pooled: true`, which is an EXTENSION — `software.md` §3 states the dedup
sizes for the numeric and alphameric kinds only (≤9 digits plus sign; 1-9 alphameric characters)
and says nothing about address constants. Two `&LABEL` operands naming the same label are the same
five characters, so pooling them is plausible and cheap; the area-defining kind is the
counter-example and is `pooled: false`, because deduplicating two work areas of the same size would
merge them.

**One plan departure, in the explicit-d check.** Plan §5.2's "The explicit d" names
`dModifiers: 'any'` — BCE, where the d **is** the compared character — as **the one exception** to
"the written glyph must be a key of that form's `dModifiers`". `operand.ts` accepts a second:
`dModifiers: 'bitmask'`, a real `table.ts` value carried by the `W`, `X` and `R` forms
(`src/core/isa/table.ts:426, 453, 803` — BBE, and the channel-2 and channel-1 status branches),
where the d is a **sum of the bits to test** and "one to six may be tested by a single instruction"
(`dmods.ts`'s `RX_STATUS_BITS`, `opcodes.md` §6.2 / A22-0526-3 p.37 Figure 36). A summed-bit d has
no enumerable key set, so there is nothing to list and no glyph to reject: the handling is right and
the plan's exception list was incomplete. `test/asm-operand.test.ts` pins it on `BBE` and `BNR1`.

### Wave 4 — pass 1 and the demo

`src/asm/symbols.ts` and `src/asm/literals.ts` are the assignment-counter walk: one pass over the
statements, in source order, that hands out every address in the program and needs no symbol value

**Four rulings recorded here because they are mechanical rather than open, and a later wave would
otherwise rediscover them.** (1) **A pooled literal's SEQNO continues past the last source card.**
`ListingLine.seqno` is "1-based over all cards" (`src/asm/types.ts`) and a processor-generated DCW
is not a card, so the flush numbers its lines from `statements.length + 1` upward. `pack()`'s
`cardOf` is keyed on SEQNO and must stay a function, which is what forces uniqueness; the listing
consequence is that the SEQNO column jumps at a flush, which is where Exhibit IV's own numbering
also stops being the card count. (2) **`SymbolEntry.duplicate` is set on the STORED entry**, not on
the later definition that earned the `M`: the later definition is never entered in the table — the
first value stands — so the stored entry is the only place the fact that a name is multiply defined
can be observed at all, and `PST` and the view both read the table rather than the listing.
(3) **An area-defining literal's label dies from the POOL and not from the symbol table.**
`software.md` §2 says those labels "die at each LTORG/SPEND and must be redefined"; the pool forgets
them, so a later section writing the same `NAME#n` gets a new allocation and no `M`, while the flat
two-pass symbol table keeps the first assignment. A reference in a later section to a name it did
not redefine therefore still resolves, where the period processor would have flagged it — the one
part of that rule a two-pass assembler with a single table cannot express, and it is written down
rather than left as a surprise for Phase 5. (4) **An LTORG whose pool is EMPTY moves the assignment
counter and NOT the high-water mark.** `software.md` §2 makes a blank ORG "the high assignment
counter + 1", and pass 1 raises that mark in `advance()` alone — which runs once per literal
actually assigned. So `LTORG 00900` in a section that pooled nothing relocates the counter to 00900
and leaves the mark where the last assignment left it, and a later blank ORG returns BELOW 00900.
Read literally that is the rule: nothing was assigned at 00900, so the high assignment counter did
not move. No source discusses the case, because a section with no literals had no reason to write
the card; the behaviour is documented at `flushPool` rather than guarded.

**WHICH CARD A RESEQ LANDS ON — a modelling choice on a `[verified]` fact, recorded here rather
than as a constant.** `software.md` §6 is `[verified]` that RESEQ "resets the object-deck sequence
to 001 and changes the ident", and it says **nothing about card boundaries**. It does not have to:
on a coding sheet the question does not arise, and it only becomes a question because our packer
fills a 60-column payload continuously across statements. The ruling: **a card takes the ident and
the sequence in force for the statement that owns its FIRST cell** — the emitted item whose
`[at, at + cells.length)` covers `record.loadAddress`, under the latest JOB or RESEQ whose seqno is
lower than that item's. A card that straddles a RESEQ therefore keeps the OLD ident and the OLD
sequence, and the rebase to 001 happens on the first card the RESEQ's own cells open. No constant
is invented for it: nothing about the machine or the manuals is in doubt, only how a continuous
packer maps a card-oriented statement.

The alternative it replaces was "the lowest `cardOf` card with a seqno at or after the RESEQ's",
and it is wrong in the ordinary case rather than an exotic one: `cardOf` records where a statement
BEGINS, so a 50-character marked DCW (2 + 49 = 51 of the 60 columns), a RESEQ, and two more
50-character DCWs pack to three cards — 00500+58, 00558+59, 00617+33 — of which card 1 holds the
whole pre-RESEQ constant AND the first eight cells of the post-RESEQ one. Keyed on `cardOf` the
whole deck comes out `001`/`002`/`003` under the RESEQ ident and the JOB's ident never reaches
paper at all; under the ruling it is `001AAAA1` / `001BBBB2` / `002BBBB2`. `test/asm-listing.test.ts`
drives exactly that deck through `pack -> withIdent -> encodeObjectRecord` and reads columns 73-80
off the punched cards, plus the boundary case where an ORG makes the two rules agree.

The same "governs what follows it" rule is what the LISTING reads: the page heading prints the
ident **in force at the top of that page** — the JOB's until a RESEQ line has been passed — and not
`Pass1Result.ident`, which is whatever the LAST JOB or RESEQ left behind and would stamp a RESEQ's
ident on pages printed before the RESEQ card existed.

**§8.3's ident map is `pack()`'s responsibility and it lives in `tools/asm.ts` — wave 6 moves it.**
The plan's §8.3 sketch gives the sequence and the ident to the packer, and `pack.ts` itself says so
("RESEQ resets the sequence to 001; that reset is the caller's"); the map sits in the CLI only
because `pack(items, reserved)` is a wave-2 signature this wave does not touch and the browser view
does not exist yet, so the CLI is currently the one caller that walks the records. That makes
`withIdent` a §8.3 function in a §3.3 file, and the divergence is written down rather than
discovered later. **Wave 6 migrates it into `src/asm/assemble.ts`** — it takes no CLI argument and
reads no CLI state, so the move is a cut and paste — **and moves the test's import with it**, where
the assertion becomes deck-level: `assemble(demos/hello-dad.asm)` yields two records punching
`001HDAD1` and `002HDAD1`. Until then `test/asm-listing.test.ts` imports `withIdent` from
`tools/asm.ts` and makes the same assertion one level down, so the migration is checkable rather
than trusted.

**A constant longer than the INSTRUCTION column is cut at 18 positions — a stated rendering rule.**
§9 sized INSTRUCTION for an instruction (`D 00394 00306 L` is 15), and an emitting DCW/DC renders
its whole constant in that column on Exhibit IV SEQNO 39's precedent — so a 40-character constant
prints its first 18 characters and no more. Nothing is lost from the page: the CT column carries
the true length and the OPERAND column carries the constant as punched. The rule is ours because no
source describes a standalone listing's constant column at all, and the only continuation form
anything publishes is the OS listing's second line for an unprintable REL field
(`console-and-physical.md` §12, C28-0326-2 Fig.2 pp.10-11) — an OS-only column Phase 3 does not
carry, so adopting its second-line form for a different column would be inventing a period
behaviour rather than reproducing one. The alternative, if a source ever surfaces: widen
INSTRUCTION, or give a long constant a second line. `test/asm-listing.test.ts` pins the 18-position
cut on a 40-character DCW.

**ADDRS is printed on the control lines too — JOB, CTL, RUN, LOAD.** They assemble nothing and
occupy nothing, and the column shows the counter as it stands when the card is read. That follows
§2.2's own precedent for an unrecognised operation ("`O`, CT 0, ADDRS = the current counter and no
emission"): the ONE RULE for ADDRS is "the address a label on this statement would resolve to",
which is defined for a control card even though no label may be written there. The one line that
prints a BLANK ADDRS is the comments card, which is text and not a statement. A rendering choice,
recorded because it is visible on the demo's own first four lines.

**`FLAG_ORDER` now lives in three files — `emit.ts`, `symbols.ts` and `listing.ts` — and that is
deliberate.** `ONE_FLAG_PER_LISTING_LINE`'s precedence `O > F > M > U` is declared at its point of
use in `emit.ts`; `symbols.ts` carries its own copy because pass 1 must decide which of two flags a
line KEEPS as it walks; and `listing.ts` carries a third because merging the two passes is a
**two-way** operation — pass 1's half and pass 2's half of the same line each may carry a flag, and
the stronger wins with its own message. A shared constant would put a listing concern in `emit.ts`
or an emission concern in `listing.ts`, so the four-element array is repeated and the reason is
written here. If it ever grows a fifth element, all three move together; the flag set is closed and
published (`software.md` §6), which is why that is an acceptable cost.
